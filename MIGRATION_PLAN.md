# Перенос SONNENBLUME на существующий домен и хостинг

Первичное исследование выполнено 13 сентября, статус обновлён 23 сентября 2026 года. На отдельном защищённом staging уже развёрнут новый frontend, WordPress CMS и backend заявок. Production, DNS, почтовые ящики и старый WordPress не переключались.

## Текущий статус

- Полный backup файлов и базы старого сайта создан и проверен вне публичного webroot.
- `staging.sonnenblume-mg.com` использует отдельный каталог и отдельную базу, HTTPS, HTTP Basic Auth и `noindex`.
- Staging-почта и внешние интеграции отключены; production-почта не менялась.
- Плагин SONNENBLUME 0.7.0 управляет шестью коллекциями и очередью обращений/регистраций.
- Новый статический frontend размещён поверх staging без удаления WordPress; `/wp-admin/` и REST API доступны.
- На production по-прежнему показывается старый сайт. Переключение возможно только после пользовательской приёмки и финальной проверки почты.

## Вывод

Наш сайт можно разместить на `https://sonnenblume-mg.com/` без покупки нового домена и без переноса почты. Для самостоятельной работы всех функций на текущем ALL-INKL потребуется адаптировать серверную часть к PHP/WordPress. Простое копирование Next.js-проекта или загрузка его ZIP как темы WordPress не подходит.

Выбранный и проверенный на staging вариант: сохранить ALL-INKL и WordPress как CMS/API, а новый визуальный интерфейс публиковать статически. Проектный WordPress-плагин хранит контент, обращения и регистрации в MariaDB; редакторы работают через штатную защищённую панель.

## Что подтверждено

- В почте найдено письмо `Fwd: Sonnenblume ALLE Passwörter` с текстовым вложением. Оно содержит доступы к Members Area, KAS, WordPress и почте. Учётные данные не сохранены в проекте или отчёте.
- Доступ KAS проверен через официальный HTTPS SOAP API. Выполнены только `get_domains`, `get_accountresources`, `get_accountsettings`, `get_server_information`.
- `sonnenblume-mg.com` активен, его текущий webspace-каталог — `/sonnenblume-mg.com/`, выбран PHP 8.2.
- `sonnenblume-mg.de` и `sonnenblume-mg.org` в KAS направлены на `https://sonnenblume-mg.com/`. Эти перенаправления нужно сохранить.
- `ssh_access=N`: SSH в текущем аккаунте отключён. Лимит webspace — 51 200 MB, баз данных пять, используется одна, свободны четыре. Название и стоимость тарифа отдельно не проверялись.
- DNS: A `85.13.137.14`; MX `w01e41a4.kasserver.com`, priority 10; NS `ns5.kasserver.com`, `ns6.kasserver.com`; SPF `v=spf1 a mx include:spf.kasserver.com ~all`.
- Публичный WordPress REST API отвечает: 37 опубликованных страниц и две опубликованные записи. Живой `wp-sitemap.xml` 26 сентября содержит 45 индексируемых URL в пяти дочерних sitemap; все 45 сохранены в `scripts/legacy-redirects.json`.
- Публичные REST namespaces показывают Contact Form 7, WooCommerce и PayPal-связанные расширения, среди прочих. В проверенном SQL-backup нет записей о товарах, заказах, покупателях, корзинах, платёжных токенах или строках заказов. Из 60 WordPress-пользователей 57 имеют роль `subscriber`, три — `administrator`; ролей `customer` и `shop_manager` нет. Поэтому `/cart/` и `/my-account/` считаются неиспользуемыми публичными заглушками, но `/wp-admin/` и редакторские учётные записи сохраняются.
- Логин WordPress, защищённый FTPS, резервная копия и отдельный staging проверены. Временный ограниченный staging-FTPS аккаунт после загрузки удалён.

Настройки аккаунта получены непосредственно из KAS, DNS — прямым запросом, содержимое WordPress — публичными GET-запросами. Пароли не передавались сторонним анализаторам.

## Почему нужен не только перенос файлов

В нашем проекте Next.js 16.3.5. Статическая сборка уже существует, но сборщик намеренно исключает `/api`, серверную админку и динамические страницы токенов. Браузер обращается к отдельному API существующего Sites-развёртывания.

| Функция                                | Статические файлы на ALL-INKL                          | Полный перенос на PHP/WordPress                    |
| -------------------------------------- | ------------------------------------------------------ | -------------------------------------------------- |
| Дизайн, страницы, фото, QR, навигация  | Работают после сборки под правильный домен             | Сохраняются                                        |
| Контактная форма и распределение писем | Нужен существующий внешний API и разрешённый origin    | Собственный обработчик, сохранение заявок и SMTP   |
| Запись, места, ожидание, отмена        | Нужен существующий внешний API                         | Перенос бизнес-логики и данных в MariaDB           |
| Панель заявок                          | Остаётся на текущем сервере, не в статическом экспорте | Раздел в WordPress с ограничением ролей            |
| Изменение контента обычным редактором  | Сейчас основное содержимое в файлах проекта            | Подключение WordPress как CMS и редакторских полей |

У проекта есть адаптер чтения новостей WordPress и транспорт Contact Form 7, но это не готовая универсальная интеграция CMS. Главная использует проектный контент; изменение старой WordPress-страницы автоматически её не обновит. Стандартная Contact Form 7 также не заменяет очередь записей, контроль мест и админку.

Согласно установленному руководству Next.js, static export подходит любому серверу HTML/CSS/JS, но не исполняет динамические API, cookies и серверные операции. В KAS подтверждён PHP, а поддержка постоянного Node.js/Next.js-процесса не установлена. Наличие PHP `exec()` само по себе не подтверждает возможность такого процесса.

## Два реалистичных пути

### 1. Быстрый промежуточный запуск

Выложить статический интерфейс на ALL-INKL, оставив действующий серверный API и его D1-базу там, где они сейчас работают. Видимый адрес станет `sonnenblume-mg.com`, но техническая зависимость от прежнего API останется. Это важно, если задача — отказаться от прежнего провайдера полностью.

Перед сборкой необходимо убрать жёстко заданный `https://garuday.github.io` из `scripts/build-github-pages.mjs` и canonical-перенаправлений в `scripts/prepare-github-pages.mjs`; задать целевой домен, API origin, sitemap и metadata. В текущем API разрешить только нужные новые origins, сохранив существующие разрешённые адреса. Без этого формы с нового домена получат отказ CORS/403.

Проверить страницу статуса по `?token=`, отмену записи, все API-запросы и ссылки на серверную админку. Админку нельзя обещать по новому домену лишь потому, что публичные страницы перенесены. При сохранении WordPress как отдельного CMS нужно отдельно организовать его URL и доступ к медиа; старый REST endpoint не должен исчезнуть после смены webroot.

### 2. Полный перенос без нового платного хостинга — рекомендуемый конечный путь

Сохранить WordPress на текущем ALL-INKL, сделать интерфейс в нашем стиле и собственный плагин:

1. REST-обработчики обращений и регистраций с серверной валидацией, ограничениями, защитой от спама и повторов.
2. Отдельные таблицы MariaDB для заявок, мест, ожидания и уведомлений; атомарные изменения, чтобы одновременные записи не переполняли событие.
3. SMTP с нынешними маршрутами `kontakt@`, `kurse@`, `vorstand@`. Пароли только на сервере; клиент не выбирает произвольный адрес получателя.
4. Сохранение текущих reference и приватных токенов отмены при переносе действующих регистраций. Закрытые данные не размещать в статике, uploads или публичном репозитории.
5. Защищённая панель заявок в WordPress, роли редактора/оператора, экспорт, сроки хранения и повторная отправка неудачных уведомлений.
6. Редактируемые новости, события, курсы, люди и партнёры. Прежние пожелания к главной, отсутствию отдельной страницы «Про нас», вакансии/форму помощи и заглушку Telegram сохранить.

WordPress REST API позволяет отдельному интерфейсу читать управляемое содержимое и расширять API плагином. Это потребует разработки и тестирования: существующий TypeScript/Nodemailer/D1 Worker нельзя исполнять в WordPress без адаптации. Переписывать дизайн с нуля не требуется, но интеграция frontend и backend является отдельной работой.

## Безопасный порядок внедрения

1. Проверить отдельные доступы WordPress и FTPS, полномочия администратора, расширения, активность WooCommerce и политику текущего хостинга. При MFA — участие владельца, без сбросов или обходов.
2. Сделать согласованный полный backup: файлы WordPress, uploads, `.htaccess`, конфигурация и экспорт базы. XML «Инструменты → Экспорт» не заменяет полный backup. Сохранить его вне публичного webroot. Перед восстановлением обязательно запустить `upload-wordpress-ftps.py --verify-only`: загрузчик не открывает FTPS, пока каждый файл не совпадёт с манифестом по пути, размеру и SHA-256. Непосредственно перед production нужен свежий финальный backup, даже если ранее проверенная копия остаётся исправной.
3. Поднять закрытый от индексации и посторонних тестовый экземпляр в отдельной папке и отдельной базе. Сначала использовать подходящий существующий preview-доступ; новый поддомен/сертификат требует настройки и не создан в исследовании. В staging отключить реальные внешние рассылки и платежи.
4. Реализовать выбранную архитектуру, импортировать контент и данные, протестировать редакторский процесс и весь функционал на компьютере и телефоне.
5. Подготовить точную карту старых URL → новых. Не отправлять каждую старую страницу на главную: сохранить архив и документы либо перенаправлять на действительно соответствующий контент.
6. После разрешения на запуск переключить только webspace-цель домена в KAS или выбранную тему WordPress — в зависимости от архитектуры. Не менять NS/MX/SPF и не удалять старую папку/базу.
7. Проверить HTTPS, www/non-www, `.de`/`.org`, глубокие ссылки, 301/404, canonical/sitemap, медиа, формы, записи, отмены и вход в админку. Один помеченный тест письма — только в рамках согласованной проверки.
8. Для отката восстановить прежнюю webspace-цель/тему; если уже появились новые заявки, сначала сохранить и согласовать их перенос, чтобы откат не потерял данные.

Провайдер официально поддерживает явный FTPS с TLS. SFTP зависит от SSH, который сейчас отключён. Не использовать обычный незашифрованный FTP и не складывать полный пароль KAS в GitHub Actions. Для будущего автодеплоя нужен отдельно согласованный ограниченный доступ только к каталогу нового сайта.

Полная однозначная карта хранится в `scripts/legacy-redirects.json`: 45 источников, 45 назначений и причина каждого решения. `npm run verify:legacy-redirects` проверяет полное покрытие, отсутствие дубликатов и циклов, существование каждой страницы/PDF в `.pages-out` и наличие якорей `verein`, `board`, `partners`. `node scripts/legacy-redirects.mjs --fetch-live` дополнительно обнаруживает изменения живого sitemap. Production-сборка создаёт HTML fallback для каждого старого адреса и отдельный `legacy-redirects.htaccess` с точными 301; этот блок нужно добавить перед штатным `# BEGIN WordPress`, не заменяя WordPress-правила.

В карте использованы существующие внутренние пути статического экспорта (`/de/courses/`, `/de/events/`, `/de/contact/`). Серверный Next.js-вариант локализует сегменты иначе; при изменении архитектуры валидатор остановит сборку, если назначение исчезнет.

## Критерии готовности к замене старого сайта

- Полный backup действительно восстанавливается; прежний сайт доступен для отката.
- Новый адрес больше не указывает canonical на GitHub; все старые существенные ссылки обработаны.
- Письма доходят по правильным маршрутам; ошибки не показываются как успешная отправка.
- Одновременная регистрация, ожидание, повторы, отмена и приватные ссылки работают; действующие заявки не потеряны.
- Редактор может менять согласованный контент без доступа к коду и секретам.
- Админские и персональные данные закрыты; тестовый экземпляр не индексируется.
- Почта домена и перенаправления дополнительных доменов продолжают работать.
- Проверены правовые тексты, банковские реквизиты и отсутствие тестовых платежей/рассылок.
