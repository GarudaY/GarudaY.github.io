# Ukrainian Verein Website Prototype

Современный сайт украинского Verein в Германии. Модули WordPress CMS для новостей, людей, курсов, событий и волонтёрских задач уже реализованы локально: правление, преподаватели, волонтёры, учебные программы, афиша и вакансии редактируются с черновиками и проверкой редактора. Остальные коллекции пока читаются из локальных данных. Регистрации на редактируемые события ещё не подключены: см. `cms/wordpress/README.md`.

## Стек

- Next.js `16.3.5`, App Router
- React `19.2.4`
- TypeScript
- Tailwind CSS `4`
- ESLint `9`
- Prettier
- Lucide React для иконок
- Zod используется для серверной валидации заявок и будущих CMS/API payloads

## Запуск

```bash
npm install
npm run dev
```

По умолчанию сайт открывается на немецком (`/de`). Украинская версия доступна через `/uk`. В серверной версии используются локализованные сегменты вроде `/de/kurse`, в статической версии — `/de/courses/`.

Ключевые публичные разделы: главная с информацией о Verein и правлением, волонтёрство, курсы и преподаватели, события и архив афиш, пожертвования, контакты и юридические страницы. Новости команды находятся только на главной. Старые адреса «Про нас» и «Щодення» перенаправляют на главную и события соответственно.

### Локальная редакторская панель

В двух терминалах:

```bash
npm run dev:cms
npm run dev:with-cms
```

Первый запуск скачивает WordPress 7.1 и PHP 8.2 WASM. Панель доступна только на `127.0.0.1:9400`; команда выводит одноразовую ссылку для локального входа (действует час). Это отдельная локальная установка, не старый сайт. База и фото сохраняются WordPress Playground вне репозитория. Не переносить эту тестовую базу или helper автоматического входа на хостинг.

Редактор работает в штатном WordPress: раздел SONNENBLUME. Есть украинские/немецкие поля, фото и alt, фокус кадра, сортировка, черновики, отправка на проверку, публикация, снятие с публикации и восстановление последних 20 версий. Роли `snb_author` и `snb_editor` не дают доступ к настройкам, плагинам, пользователям или заявкам. Пользователей в рабочем WordPress создаёт владелец; плагин сам не создаёт аккаунты.

На серверном frontend `WORDPRESS_CMS_URL` задаётся в окружении: новости, люди, курсы, события, волонтёрские задачи и партнёры читаются из публичного API с кешем 60 секунд. Нет админских паролей на frontend. Без CMS сохраняется локальный контент. При недоступности настроенного CMS новости могут показать подписанные примеры, но люди, курсы, события, вакансии и активированный список партнёров не подменяются старыми списками: появляется сообщение о временной недоступности. Для партнёров старый список действует до явного переключения редактором; после этого даже пустой feed остаётся пустым. Форма для собственной волонтёрской идеи остаётся доступной. GitHub Pages фиксирует шесть feed в одном проверенном снимке во время сборки — для обновлений нужна повторная сборка.

Установка на существующий WordPress и остальные разделы описаны в [CMS README](cms/wordpress/README.md). Пока плагин не установлен на рабочем/тестовом хостинге, редакторы извне не могут пользоваться этой локальной панелью.

## Demo-контент

Данные правления, преподавателей, адрес, реквизиты и основные фотографии перенесены из предоставленных материалов. Примеры внутренних новостей отдельно помечены в интерфейсе. Волонтёрские роли описывают возможные способы помочь; конкретные задачи команда согласует с заявителем.

Регистрация на событие и контактная форма работают через локальные Route Handlers. Данные атомарно сохраняются в исключённый из Git файл `.data/operations.json`; поддерживаются duplicate-защита, остаток мест, waitlist, приватная отмена, статусы обращений и CSV-экспорт. Локальная панель доступна на `/uk/admin` и `/de/admin` только через localhost. Подробности и ограничения описаны в `OPERATIONS.md`.

Почтовая доставка работает через серверный SMTP-транспорт; ошибка доставки отображается отдельно от сохранения заявки. После регистрации пользователь получает номер и приватную ссылку прямо в интерфейсе. Существующий Sites/Cloudflare API сохраняет данные в D1. Подробности подготовки и проверок — в `HOSTING_READY.md`.

## Замена логотипа и изображений

- Временный знак находится в `src/components/layout/SiteLogo.tsx`. Чтобы заменить его централизованно, измените только этот компонент; Header и Footer используют его повторно.
- Demo-фотографии находятся в `public/images/generated/`, партнерские знаки — в `public/images/partners/`. Путь и локализованный `alt` задаются в `src/content/mock/*` через `ImageAsset`.
- `ContentImage` сохраняет контракт: WordPress-фото валидируются адаптером и отдаются напрямую без Next image-proxy; поддерживаются переведённый alt, `fill`, стабильная рамка и вертикальный фокус.

## Переход на CMS

Выбран WordPress на существующем хостинге, без нового платного редакторского сервиса. Дизайн остаётся в Next.js. Локально работают новости, люди и курсы, роли, черновики, публикация, фото, связи преподавателей и история. Детали — в `cms/wordpress/README.md` и `ADMIN_CMS_PLAN.md`; старый `CMS_PLAN.md` про Sanity больше не является текущим решением.

## Публичный demo-хостинг

Публичный сайт: https://garuday.github.io/de/

Ветка `code` содержит исходный проект. Ветка `source` сохраняет статическую копию и запускает `Deploy GitHub Pages`. Публикация разрешена для ветки `source` в существующем окружении `github-pages`.

Workflow заново получает актуальную ветку `code`, устанавливает зависимости через `npm ci`, запускает линтер, проверку подготовки статического экспорта (`npm run test:pages`) и `npm run build:pages`, затем публикует только `.pages-out`. Для публикации нужно сначала отправить исходный коммит в `code`, затем обновить `source` с новым workflow. Ручной запуск Actions из `source` также пересобирает актуальный код.

Локальная статическая сборка:

```bash
npm run build:pages
```

Подготовка архива сохраняет старые ссылки через HTML-переадресации и нормализует файлы предварительной загрузки Next.js при сборке на Windows. Один и тот же архив можно обслуживать обычным статическим сервером без скрытых 404 навигации.

GitHub Pages обслуживает HTML, CSS и изображения. Формы используют существующий серверный API, заданный через `NEXT_PUBLIC_API_BASE_URL` при сборке; серверные обработчики и админка не включаются в статический архив.

Cloudflare/OpenNext-сборка и готовый bundled Worker создаются командой:

```bash
npm run bundle:sites
```

Для существующего Sites/Cloudflare API устанавливается runtime-переменная `HOSTED_DEMO=true` и используется постоянная D1-база с binding `DB`. Локальный режим без этой переменной использует `.data/operations.json`. Нельзя включать этот режим на другом хостинге без подключения `DB`.
